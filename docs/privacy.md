# Privacy preprocessing

Phase 9 introduces an internal privacy boundary before the supervisor and LLM-backed components.
It implements deterministic synthetic-data privacy controls for the clean-room
reconstruction; it is not a claim of comprehensive clinical free-text de-identification or any
formal compliance certification.

## Position in the request flow

The intended flow is:

```text
user text
  -> PrivacyProcessor
  -> SupervisorMultiAgent
  -> future specialist

LLM or specialist response
  -> ResponseUnmasker
  -> user-facing response
```

`PrivacyProcessor` is internal infrastructure. It has no HTTP route and does not call FastAPI,
`SessionStore`, PostgreSQL, `QueryExecutor`, or an LLM. Phase 10's supervisor is designed to accept
the resulting `safe_text`; future `ChatService` orchestration will enforce this composition.
Specialist execution, NLP-to-SQL logic, and `POST /chat` remain unimplemented.

## Reversible business identifiers

Exact external identifier formats generated by the Phase 3 seeder are supported:

| Type | Format | Example |
|---|---|---|
| Facility | `F` plus 4 digits | `F0042` |
| Provider | `P` plus 5 digits | `P00125` |
| Member | `M` plus 6 digits | `M000245` |
| Encounter | `E` plus 7 digits | `E0000125` |
| Claim | `C` plus 7 digits | `C0000789` |
| Appointment | `A` plus 7 digits | `A0000042` |

Each distinct identifier is assigned `T001`, `T002`, and so on in first-occurrence order. Repeated
identifiers reuse their token. Allocation starts fresh for every `process()` call and uses no
global mutable map. Standalone `Txxx` values already in the input are reserved, so generated tokens
cannot collide with them.

The result retains one ordered `TokenMappingEntry` per distinct identifier. This token-to-original
information is sensitive internal state: application privacy code does not log it, place it in
metadata or flags, expose it through an API, or include its values in errors.

## Irreversible generic PII redaction

The deterministic baseline recognizes:

- conventional email addresses with a dotted domain, replaced by `[EMAIL]`
- formatted US phone values such as `(415) 555-0137`, `415-555-0137`, and
  `+1 415 555 0137`, replaced by `[PHONE]`

Email and phone values are not kept in the reversible mapping. Short analytical numbers such as
`5`, `1000`, `2500`, and `2026` do not match the phone detector. Dates are deliberately preserved
because they are essential analytical criteria.

Identifier spans are detected with explicitly ordered patterns and replaced from right to left.
Generic redaction then processes emails before phones, also using validated right-to-left span
replacement. That ordering prevents a phone-like email local part from being partially changed.

## Request scope and sessions

`PrivacyResult` contains safe text, ordered current-request token mappings, and non-sensitive
occurrence counts. It can derive the serializable token-to-original dictionary compatible with
`SessionState.last_token_mapping`. The processor never writes that field itself; a future
`ChatService` will own orchestration and session updates.

`token_mapping_history` is intentionally absent from persisted `SessionState`. Retaining mappings
across requests would unnecessarily extend the lifetime of protected values and could restore an
unrelated token from a later response. `custom_context` also remains non-durable session input.

`ResponseUnmasker` accepts response text and only the current request's mapping. It restores known
standalone generated tokens, leaves unknown tokens unchanged, does not replace token-like text
inside larger words, and never restores `[EMAIL]` or `[PHONE]`.

## Complete synthetic example

```text
Original:
Show claims for member M000245 and send results to alice@example.com.

Safe LLM text:
Show claims for member T001 and send results to [EMAIL].

Current internal mapping:
T001 -> M000245

Model-style response:
Member T001 has 4 claims. Results cannot be emailed to [EMAIL].

Unmasked user response:
Member M000245 has 4 claims. Results cannot be emailed to [EMAIL].
```

The original identifier and email do not cross the LLM boundary in this example. Only the business
identifier can be restored; the email remains redacted.

## Known limitations

- Detection is exact and case-sensitive for the six seeded external identifier formats.
- It does not identify arbitrary long numbers, internal database primary keys, names, addresses,
  medical record numbers, or unformatted phone digits.
- It does not attempt generic rule-based person-name recognition and never loads names from the
  healthcare database.
- Dates, including possible dates of birth, are not contextually classified or redacted.
- Free-text clinical narratives can contain sensitive content outside these deterministic rules.
- Production deployments may require stronger policy controls and dedicated privacy services based
  on their risk assessment and regulatory obligations.
